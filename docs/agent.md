# Agent 使用方向与结果语义

本文记录 RepoCargo 的接口方向与现有边界，供后续整理源码和验收使用；它不是已实现的新 CLI 规范。

## 已有基础

原项目的 `gitbigfileftpcli` 是独立 Rust 包装器，静态识别并启动已有后端。它区分旧参数原样转调和结构化调用；结构化入口包含项目状态、操作计划及 JSON 输出等能力。

它的能力与约束来自实际后端。Python 完整版、Rust 精简版和 Net 下载器的能力有区别，现有 CLI 也不能被描述为 Net 下载器的统一启动器。

源码迁入后，应先补齐实际命令、能力和测试的对应关系，再确定 RepoCargo 对外公开的接口；准备阶段不重命名已有命令，也不添加新的业务功能。

## Agent 需要理解的四类信息

| 信息 | 需要表达的内容 |
| --- | --- |
| 项目状态 | 配置位置、资源根、资源清单、版本或目录标识、本地存在性与可用的校验结果 |
| 执行计划 | 后端、实际路径与目标地址、涉及的文件，以及覆盖、删除、环境修复等副作用 |
| 执行结果 | 执行到哪个阶段、哪些文件完成、哪里失败、是否仍存在未恢复的资源 |
| 证据边界 | 哪些结论由索引、文件摘要、实际读写或传输结果证明，哪些尚未验证 |

这里列出的是整理和演进方向，不能将尚未核实的字段当成现有 JSON 输出承诺。

## 结果语义

Agent 需要根据可核验结果判断操作，而不能只读取一句“完成”：

- 已生成计划、已启动后端、后端已退出、传输已结束、文件校验通过，是不同的状态。
- 后端正常退出，不自动等于全部资源已恢复且校验通过。
- 文件存在或大小为零，不足以判断下载成功；合法空文件与失败后留下的空文件必须区分。
- 已取得版本标识，不自动等于对应快照和资源已成功取得。
- 下载失败后是否保留旧文件、是否留下临时文件、是否继续清理，必须按具体实现说明。

原 Python 协议资料中的 D21/D22 涉及 FTP 下载错误被吞掉，已经为默认下载入口做过最小修复。后续迁移须连同正式回归测试和兼容说明一起保留，不能仅凭文档宣称修复仍有效。

## 副作用与自动化

已有程序中，上传、下载、清理和“仅索引”可能有不同副作用。部分流程还包含复制、删除、Git 暂存、PDB/dSYM 处理或环境修复。

后续接口需要让 Agent 在执行前理解这些事实。不能仅凭参数名称推断操作只读，也不能通过包装器隐藏后端的失败或副作用。

自动化验收优先采用独立临时项目和受控传输夹具，明确标注真实文件行为、模型测试与外部工具模拟。不同平台和不同后端应分别记录能力与证据，未实现的功能不因为接口方向而自动成为旧版本必须补齐的要求。
