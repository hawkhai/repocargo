# 源码迁移与兼容约定

当前阶段只整理 RepoCargo 新仓库的说明和迁移准备，不修改原 Python、Rust、Net、CLI 或协议测试源码，也不导入原工作区尚未提交的改动。

## 品牌与兼容

对外项目名称采用 **RepoCargo**，仓库为 [hawkhai/repocargo](https://github.com/hawkhai/repocargo)。

原项目沿用的程序名、目录名、旧斜杠参数、`gitbigfilex.json`、目录 ID 文件、索引、版本快照和 ZIP 命名仍有兼容价值。品牌名称的变化不自动改变这些协议内容。

源码迁入时，先保留原文件布局和已有入口。后续若需要新的命令名或别名，应单独说明兼容方式并验证，避免全局文本替换引入路径、资源引用或程序识别问题。

## 迁移步骤

1. **确定来源版本**：为每个实现记录已选定的提交；单独处理仍在进行的工作区改动。
2. **整理依赖**：确认 Rust 路径依赖和 Python 的 pythonx 共享依赖，让新目录中的导入、构建和测试有明确入口。复制一个 Python 文件不等于得到可独立运行的完整版本。
3. **迁入源码与测试**：保留来源和必要的资源/许可资料；不把凭据、缓存、下载数据或编译输出混入源码迁移。
4. **验证原有能力**：以 Python 完整版为业务基准，各实现仅验收已实现的功能；按实际平台标注通过、失败、跳过与模拟范围。
5. **更新新仓库用法**：只有在新目录下实际验证后，才补充可复制的构建、运行和测试命令。
6. **再整理发行与 Agent 入口**：统一对外说明、能力识别和结果语义；有意改变兼容行为时，单独列出变更和回归证据。

以上是后续工作顺序，不表示本轮已实施源码迁移、构建或发行。

## 协议与测试

协议文档和测试首先描述既有行为。现有约定、当前限制和真正 bug 需要分别记录；不能把未实现的新要求写成旧版必须满足的预期。

确认修复的 bug 应保留编号和回归案例，并明确新旧行为。未修复问题按现有结果复现，测试通过不等于这些问题已经消失。D21/D22 的错误传播修复与其他现存路径问题也应分别追踪。

mainroot、平台路径、斜杠/反斜杠、尾分隔符，以及失败后的文件和清理状态，是迁移时需要保留的重点验收内容。

## 当前未包含的事项

本仓库尚未包含业务源码、构建脚本、可执行文件、正式发行包或新的配置格式。现阶段不提供假定源码已经迁入的安装和运行命令；后续文档随实际迁移与验证结果更新。
