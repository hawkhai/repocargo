# GitLab 管理员授权与验收

## 应用仓库

1. 每个应用建立独立私有项目，按公司规则选择命名空间。首次接收已有项目时，不初始化 README、许可证或其他远程提交。
2. 从项目页面复制实际 **SSH 克隆地址**。请使用自己的 GitLab 服务；文档中的 `gitlab.example.invalid` 是不可连接的占位符。网站地址不能证明 SSH 使用哪个端口或是否需要 VPN，必须实际确认。
3. 客户运行 `repogit device init`，只向你提供 `.pub` 公钥及指纹。核对设备和客户身份后再授权。
4. 在项目 Settings → Repository → Deploy Keys 添加公钥，建议名称包含客户、设备标识和日期。按需勾选写权限并设置到期时间。
5. 第一位上传者执行 `bind`、`doctor` 和 `push`。第一次推送创建默认 `sync` 分支。只读设备需要由其他获准写入的设备先创建分支。

工具不需要客户拥有 GitLab 账号，也不需要客户持有你的 SSH 私钥或 API Token。Deploy Key 与创建它的 GitLab 用户仍有关联；创建者被封禁、权限变化或密钥到期可能影响访问。持续运营时按公司政策使用稳定的自动化身份。

## 限制只能写同步分支（需要时启用）

工具自身不允许强推，默认只推绑定分支；持有设备私钥的人仍可以绕过工具使用普通 Git。因此服务器端限制不能用客户端设置代替。

在公司的实际 GitLab 版本中配置并验证：

- 使用覆盖全部分支的保护规则作为基础，不向客户 Deploy Key 广泛开放分支推送。
- 对允许的同步分支（默认 `sync`）设置允许推送的具体读写 Deploy Key；关闭强推。
- 按公司需要保留管理员/维护者权限，确认客户端密钥不能推送 `main`、新建其他分支或删除受保护分支。
- 为全部标签配置适当保护，不能只保护分支。
- 审查项目和组中的所有重叠规则。GitLab 多数权限按**最宽松匹配规则**计算，单独设置某条“禁止”规则不保证能覆盖其他规则。

若公司版本/策略不支持所需规则组合，应如实将边界定为“仓库级读写”，不能宣称具备严格分支级授权。Deploy Key 没有分支级读取隔离，源码互相保密的应用必须分仓库。

## CI/CD

客户首次推送可能触发仓库中的流水线。先用不含生产变量、Runner 凭据或生产部署权限的测试项目验证；是否启用应用的 CI/CD 按实际业务决定。Deploy Key 可读写代码不代表具有管理项目或调用所有 GitLab API 的权限。

## 实际环境验收清单

以下操作只在专用测试项目中完成，不要对生产仓库做拒绝/删除测试。

| 场景 | 预期 |
| --- | --- |
| 独立设备 A 获得读写授权 | `doctor` 可读，首次 `push` 创建 `sync`，后续更新保留历史 |
| 新设备 B 独立授权 | 可 `clone`，继续提交并推送，A 可快进拉取 |
| A 修改文件但不提交 | 推送只上传旧提交，本地文件保持不变 |
| A、B 从同一提交分别开发 | 后推送方被拒绝；拉取分叉也停止，不自动强推或合并 |
| B 只有只读授权 | 可读取，不能推送 |
| B 操作另一个未授权的私有项目 | 被 GitLab 拒绝 |
| 撤销 B 在该项目的授权 | B 新建连接后读取、推送均失败 |
| 断网、端口错误、缺少 VPN | 错误明确，已有本地提交和文件不丢失 |
| GitLab 主机密钥不匹配 | SSH 拒绝；管理员核验后按公司流程更新，不能关闭检查 |
| 配置严格分支/标签规则 | 即使直接使用普通 Git，也不能向其他分支/标签写入，不能强推 |

需要停用设备时，在每个获准项目中撤销其 Deploy Key。仅移除设备上的程序或本地绑定不会撤权；同一公钥获准多个项目时要逐一处理。已下载的源码不能通过撤权收回。
