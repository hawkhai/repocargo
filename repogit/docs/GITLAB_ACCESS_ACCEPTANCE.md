# RepoGit 0.2.0 授权配置流程：实测范围

本页专门记录 0.2.0 的 access create/show 与 bind/clone --config 流程，不能沿用 [0.1.0 历史实测](GITLAB_ACCEPTANCE.md) 的通过结论。

本地自动化使用真实 OpenSSH 密钥生成、固定口令加解密和 SSH 配置解析，再通过本地测试传输运行 Git。覆盖配置交付、独立接收端导入、普通 Git 推送、克隆/拉取、worktree/bare、配置损坏与冲突，以及模拟只读/撤权错误。测试传输不等于真实 GitLab；以当前 VALIDATION.json 的实际构建结果为准。

## 真实 GitLab 授权文件流程实测

2026-10-29，使用通过干净构建门禁的 0.2.0 发布 EXE 连接真实私有测试项目完成验证。EXE 的精确 SHA-256 见 [机器可读摘要](GITLAB_ACCESS_ACCEPTANCE.json)，不能将此结论自动沿用到其他哈希的成品。

**发送端和接收端是同一台 Windows 电脑上的两套隔离环境，不是两台物理电脑。** 两端导入同一份专用授权文件，分别保存本机密钥、主机信任和 SSH 配置，验证的正是“把一份配置交给同事”的流程。它们使用同一 Deploy Key，撤销后两个副本同时失效。

| 场景 | 结果 |
| --- | --- |
| access create/show | 生成固定口令加密的独立凭据，公开摘要不含私钥；管理员用输出公钥授权 |
| 发送端 bind --config、重复导入、doctor | 成功，重复导入不改变 Git 配置，无口令或主机信任确认输入 |
| 发送端推送已有提交 | 成功，保留原有 origin 和提交历史 |
| 接收端 clone --config | 成功，不需要预先安装密钥或建立主机信任 |
| 发送端更新，接收端 pull | 成功快进到同一提交 |
| 接收端使用普通 Git 推送，发送端拉取 | 成功，沿用导入的身份，无口令输入 |
| 配置包含错误主机公钥 | 真实 SSH 握手拒绝连接，未关闭主机验证 |
| 管理员撤权后两个副本的 doctor/pull/push | 6 次访问全部被公钥认证拒绝 |
| 撤权后重新 clone --config、普通 Git push | 均被公钥认证拒绝；合计 8 次拒绝请求 |
| 撤权后本地数据及服务器对照 | 两端文件和 HEAD 保留；另一仍获授权的测试身份可读取，远程 sync 不受拒绝请求影响 |

doctor、clone、push 的认证拒绝退出码为 128，pull 为 1；均依据明确的 `Permission denied (publickey)` 判断，并用仍获授权的身份排除整体网络故障。

公开摘要不包含真实服务地址、项目路径、本机路径、密钥或原始日志。上述真实实测是在构建测试完成后，针对同一 EXE 单独执行；发行文档及 ZIP 随后补充这份结果，EXE 未重编译。

两台物理电脑、跨网络、0.2.0 授权文件的真实只读权限、严格分支/标签保护、Git LFS 和子模块未在本轮实测；只读权限的旧流程证据见 0.1.0 历史记录，新的自动化本地测试另有模拟覆盖。
